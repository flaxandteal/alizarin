---
title: Extension ABI
description: Frozen C ABI contract for out-of-tree datatype extensions and derive providers (ABI v5)
---

Out-of-tree datatype extensions plug into alizarin through a small C ABI. An
extension builds a `TypeHandlerInfo` — function pointers into its own compiled
code — and hands it to the host, which adapts it into the shared
`ExtensionTypeRegistry` that core and every binding use. **The base crates carry
no extension dependencies**: extensions plug in at the boundary, never by
compile-time linking. The machinery that reads a `TypeHandlerInfo` and calls its
fn-pointers lives once in `alizarin-core` (`extension_abi`); the bindings are thin
front-ends over it. The same ABI also carries
[derive providers](#derive-providers) (a `DeriveProviderInfo`), whose host side
lives in `alizarin-core` (`derive_abi`).

This document is the committed contract for 2.0. `ABI_VERSION` is **5**.

> **How each binding registers the same `TypeHandlerInfo`:**
> - **Python** — wraps the pointer in a `PyCapsule`; `import alizarin_clm` calls
>   `alizarin.register_type_handler(capsule)`.
> - **NAPI** — the extension's native module passes the pointer through JS as a
>   `BigInt` to `registerExtensionHandler(ptr)`. Same C ABI, no static linking
>   (base `alizarin-napi` no longer compiles the handler cores in).
> - **WASM** — a *different*, JS-callback mechanism (portable code can't pass raw
>   pointers): `registerExtensionHandler(datatype, { coerce, renderDisplay,
>   resolveMarkers, validate, nodeConfig, displayAsList, foldIdentity, fold,
>   foldMerge, foldRemove, foldMayMatch })`, each optional (at least one of
>   `coerce`, `renderDisplay`, `resolveMarkers`, `validate`, `nodeConfig` or
>   `foldIdentity` is required). "Freeze the extension ABI" means freeze this
>   C-ABI capsule/pointer contract; the JS-callback surface is versioned with the
>   `alizarin` package.

## The surface

`TypeHandlerInfo` (in `alizarin-extension-api`) carries a datatype name, an
`AbiFingerprint`, and optional function pointers for each capability the
`ExtensionTypeHandler` trait declares. Each capability a handler provides is a
`Some(fn)`; the rest are `None`, and the host reports `HandlerCapabilities` from
which pointers are present.

| Capability | Fn pointer (+ free) | Contract |
|---|---|---|
| coerce | `coerce_fn` / `free_fn` | raw value (JSON bytes) → `CoerceResult` (tile + display). `None` ⇒ core keeps coercion. |
| display render | `render_display_fn` / `free_display_fn` | resolved value + language → display string |
| resolve markers | `resolve_markers_fn` / `free_resolve_markers_fn` | resolve `__needs_rdm_lookup` etc. after coercion |
| validate | `validate_fn` / `free_validate_fn` | value **by pointer** + config → `ValidationResult` |
| search render | `render_search_fn` / `free_render_search_fn` | value **by pointer** + language → `Option<Value>` (search-indexable JSON) |
| index spec | `index_spec_fn` / `free_index_spec_fn` | value **by pointer** + config → `Option<IndexSpec>` (semantic `IndexClass` + **raw** keys) |
| node config | `node_config_fn` / `free_node_config_fn` | raw node config **by pointer** → the datatype's normalised config (`null` for none); core models only its own datatypes' configs |
| list display | `display_as_list_fn` (no free) | raw node config **by pointer** → `bool`: does a value display as a list of labels? |
| fold | `fold_identity_fn`, `fold_fn`, `fold_merge_fn`, `fold_remove_fn` / `free_fold_fn` | reduce many values into a summary (for [aggregate functions](/docs/functions#aggregate-functions)). A summary from `fold_identity_fn` opts in, and then `fold_fn` and `fold_merge_fn` are required; `fold_remove_fn` is optional (`null` ⇒ host re-folds). Values pass **by pointer**, a batch as an array of pointers |
| fold match | `fold_may_match_fn` (no free) | summary + predicate **by pointer** → `bool`; conservative, `false` only when nothing folded can match |

Everything after the first three capabilities passes values **by pointer** (`*const
serde_json::Value`) — no per-value serialization on the hot path. The small
result (a serialized struct or an error string) is the only thing marshalled
back, and it is freed via the paired `free_*` pointer (where there is one).

### Design principle: declare semantics, not structure

`index_spec` returns the **semantic index class** (`ConceptHierarchical`,
`Ordered`, `SpatialBbox`, `Link`, …) plus the **raw** keys (ids/values). A
handler declares *what kind of index* its datatype needs — it does **not** choose
the coarse grouping, the head-table layout, or the partition granularity. All
coarsening (concept-hierarchy DFS-intervals, bbox extraction, quantization) lives
in the index **emitter** (e.g. ros-madair), keyed off the class. This keeps
storage/query structure out of the extension surface: an extension author never
needs to know the consumer's parquet/head layout.

There is deliberately **no `coarse` parameter** on the ABI — it would force
structural knowledge into the handler.

## The handshake

`TypeHandlerInfo` carries an `AbiFingerprint`:

```rust
AbiFingerprint {
    version: ABI_VERSION,                          // 5
    value_size: size_of::<serde_json::Value>(),
    handler_info_size: size_of::<TypeHandlerInfo>(),
}
```

The host checks `info.abi == abi_fingerprint()` **at registration**. A mismatch
is refused with an error **before any pointer is dereferenced** — so a stale
extension fails loudly at load, never corrupting memory.

### Soundness constraint (read before shipping an extension)

Pointer-passing `*const serde_json::Value` across the `.so` boundary is sound
**only when core and the extension share the same `serde_json`** (same memory
layout for `Value`). In practice this means: build extensions against the **same
workspace lockfile and toolchain** as the alizarin they load into. The
fingerprint's `value_size` is the guard — a `serde_json` whose `Value` size
differs is refused. (Same-size-but-reordered layout is only caught by the
`version` field, which is why the versioning policy below is strict.)

## Versioning policy

**Bump `ABI_VERSION`** on any change that alters the binary contract:

- adding, removing, or reordering a field in `TypeHandlerInfo`;
- changing any `*Fn` / `*Result` signature or layout;
- a `serde_json` major bump that changes `Value`'s layout;
- any change to the semantics a fn pointer promises.

Additive changes are **not** silently compatible: adding a fn pointer changes
`size_of::<TypeHandlerInfo>()`, so the fingerprint mismatches and old extensions
are refused (safely) until rebuilt. That is intended — there is no partial-ABI
loading. Bump the version, rebuild the in-tree extensions (CLM, filelist, geo),
and cut a coordinated release.

`ABI_VERSION` history:
- **1** — coerce, display, resolve_markers, validate; fingerprint handshake.
- **2** — added `render_search` and `index_spec`.
- **3** — added `node_config` and `display_as_list` (reference node config moved
  out of core into the CLM extension).
- **4** — added the fold functions (`fold_identity`, `fold`, `fold_merge`,
  `fold_remove`, `fold_may_match`).
- **5** — added `DeriveProviderInfo` and `HostGraph`, so extensions can provide
  derive functions.

## Derive providers

An extension can also export a [derive function](/docs/functions#derive-functions-computed-tiles)
as a `DeriveProviderInfo`: an `AbiFingerprint`, the provider id that graph
declarations name in their `provider` key (e.g. `"utm"`), a `derive_fn` and its
`free_fn`. The host registers it in the global functions registry under that id,
checking the fingerprint first.

Each call passes the resource id, its tiles (a JSON array) and its
`DeriveConfig` — with the declared `nodes` already **resolved** to node id,
nodegroup, datatype and alias — all **by pointer**, plus a `HostGraph`: a
`lookup(ctx, kind, key)` callback answering the graph's root
(`LOOKUP_ROOT`), a node by alias or id, or a nodegroup by id. Nothing
graph-sized crosses the boundary; a provider that needs listings (every node,
edges, cards) must run in-process. The result is the derived tiles as a JSON
array, freed via `free_fn`.

The extension side is written once against core's `DeriveProvider` trait:
`alizarin_core::derive_abi::derive_with` adapts the C call to it, and
`derive_provider_info(id, derive_fn)` builds the static info. Each binding
registers the same provider:

- **Python** — `alizarin.register_derive_provider(capsule)`, returning the
  provider id.
- **NAPI** — `registerDeriveProvider(ptr)` on `@alizarin/napi` with a `BigInt`
  pointer, returning the provider id.
- **WASM** — `registerDeriveProvider(providerId, { derive(resourceId, tiles,
  config, lookup) })` from `alizarin`, where `lookup(kind, key)` uses the same
  kinds (0 root, 1 node by alias, 2 node by id, 3 nodegroup by id).

`hasDeriveProvider(providerId)` (`has_derive_provider` in Python) reports
whether one is registered.

## Writing an extension (sketch)

Build the `TypeHandlerInfo` once in the extension's **core** crate
(`ext/<x>/core`, module `c_abi`), so the Python and NAPI bindings share a single
copy of the `extern "C"` wrappers:

```rust
// ext/<x>/core/src/c_abi.rs — a Once-initialised static (a constructor sets abi +
// the unused pointers to None; or a struct literal for a multi-capability
// handler, with `abi: abi_fingerprint()`):
pub fn handler_type_info() -> *const TypeHandlerInfo { /* … */ }
```

Each binding hands that pointer to the host:

```rust
// ext/<x>/python — wrap in a PyCapsule (pointer from core):
//   alizarin.register_type_handler(get_handler_capsule())

// ext/<x>/napi — hand the pointer to JS as a BigInt:
//   #[napi] fn xHandlerPtr() -> BigInt { core::handler_type_info() as u64 }
//   // then in JS: registerExtensionHandler(xHandlerPtr())  // @alizarin/napi
```

The in-tree extensions are the reference implementations: `ext/clm` (coerce +
display + resolve_markers + index_spec + node_config + display_as_list — a
`reference` is a controlled-list value, so it head-indexes as
`ConceptHierarchical`, exactly like the core `concept` datatype), `ext/filelist`
(coerce + display), `ext/geo` (validate + fold, and the `utm` derive provider).

## Packaging (npm)

Native NAPI handlers ship as a **separate** package per extension —
`@alizarin/<x>-napi` — because native `.node` binaries are per-platform (unlike
portable WASM, one artifact for all). To keep a **single import** for consumers,
the JS/WASM package `@alizarin/<x>` lists `@alizarin/<x>-napi` (and
`@alizarin/napi`) as **optional peer dependencies**
(`peerDependenciesMeta: { optional: true }` — npm won't auto-install them) and
wires them at runtime only when present:

```ts
// @alizarin/<x> entry, after its WASM registration:
try {
  const napi = await import("@alizarin/napi");
  const ext  = await import("@alizarin/<x>-napi");
  napi.registerExtensionHandler(ext.xHandlerPtr());
  // and, for an extension with a derive provider (as geo's utm):
  // napi.registerDeriveProvider(ext.xDeriveProviderPtr());
} catch { /* WASM-only consumer, or the napi ext isn't installed */ }
```

A browser/WASM consumer of `@alizarin/<x>` pulls **no** native binary; a NAPI
consumer adds `@alizarin/<x>-napi` to its deps and the same `import
'@alizarin/<x>'` covers both backends. "Combine the import, split the binary."
